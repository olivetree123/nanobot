# checkpoint
`checkpoint` 的作用是：把“本轮 agent 正在运行到哪里了”临时保存下来，防止进程中途退出后，这一轮对话完全丢失。

在主流程里，它对应的是 `session.metadata["runtime_checkpoint"]`。

## Checkpoint 结构

Checkpoint 包含以下关键信息：
- `phase`: 执行阶段（如 "awaiting_tools"）
- `iteration`: 当前迭代次数
- `assistant_message`: 助手的消息和工具调用
- `completed_tool_results`: 已完成的工具结果
- `pending_tool_calls`: 待执行的工具调用


## 作用

它保存的是“进行中的一轮对话”的中间状态，比如：

- 模型已经生成了一条 `assistant_message`
- assistant 请求调用哪些工具
- 哪些工具已经执行完并返回结果
- 哪些工具还没执行完
- 当前处于哪个阶段：`awaiting_tools`、`tools_completed`、`final_response`

如果 agent 在工具调用中、模型回复后、保存 session 前崩溃，下次处理新消息时可以把这些内容补回 `session.messages`，让历史不断裂。

## 在哪里被创建

checkpoint 的内容是在 `nanobot/agent/runner.py` 的 `AgentRunner.run()` 里创建的。

主要有三处：

1. 模型决定要调用工具后，创建 `awaiting_tools` checkpoint

```python
{
    "phase": "awaiting_tools",
    "assistant_message": assistant_message,
    "completed_tool_results": [],
    "pending_tool_calls": [...]
}
```

意思是：assistant 已经发出了工具调用，但工具还没执行完。

2. 工具执行完成后，创建 `tools_completed` checkpoint

```python
{
    "phase": "tools_completed",
    "assistant_message": assistant_message,
    "completed_tool_results": completed_tool_results,
    "pending_tool_calls": []
}
```

意思是：assistant 的工具调用和工具结果都已经有了。

3. 模型给出最终文本后，创建 `final_response` checkpoint

```python
{
    "phase": "final_response",
    "assistant_message": messages[-1],
    "completed_tool_results": [],
    "pending_tool_calls": []
}
```

意思是：最终回复已经生成，但还没确保被外层保存进 session。

## 在哪里被写入

真正写入 session 的地方在 `nanobot/agent/loop.py`。

`_run_agent_loop()` 里定义了一个内部回调：

```python
async def _checkpoint(payload):
    if session is None:
        return
    self._set_runtime_checkpoint(session, payload)
```

然后把它传给 runner：

```python
checkpoint_callback=_checkpoint
```

runner 每次调用 `_emit_checkpoint(...)`，最终都会走到：

```python
def _set_runtime_checkpoint(self, session, payload):
    session.metadata[self._RUNTIME_CHECKPOINT_KEY] = payload
    self.sessions.save(session)
```

也就是写入：

```python
session.metadata["runtime_checkpoint"] = payload
```

并立即保存 session。

## 在哪里被读取

读取发生在 `_process_message()` 一开始，拿到 session 后就会尝试恢复：

```python
if self._restore_runtime_checkpoint(session):
    self.sessions.save(session)
```

`system` 消息路径和普通用户消息路径都会做这一步。

真正读取 metadata 的方法是：

```python
checkpoint = session.metadata.get(self._RUNTIME_CHECKPOINT_KEY)
```

也就是 `_restore_runtime_checkpoint()`。

它会把 checkpoint 转成普通历史消息：

- `assistant_message` 加回 `session.messages`
- `completed_tool_results` 加回 `session.messages`
- `pending_tool_calls` 变成错误 tool 消息：`Task interrupted before this tool finished.`

恢复完以后会清掉 checkpoint：

```python
self._clear_runtime_checkpoint(session)
```

一句话总结：`checkpoint` 是“本轮 agent 的临时进度备份”；`runner` 创建它，`loop` 写入 `session.metadata`，下一次 `_process_message` 开头读取并恢复，成功完成一轮后再清除。


## 注意事项

- Checkpoint 是临时的运行时机制，恢复后会被清除
- 与会话的持久化消息不同，checkpoint 只在内存中短期保存，用于崩溃恢复

## 疑问
> 用户和system 的每一条新消息都会调用 _process_message 吗？那是不是每个新消息都会尝试恢复中断？

基本可以这么理解：进入主 agent 处理链路的每条新消息，都会调用 `_process_message()`。

包括两类：

- 普通用户消息：`msg.channel != "system"`
- 内部/system 消息：`msg.channel == "system"`，比如后台任务、subagent follow-up 之类

所以是的，每次 `_process_message()` 开始时，都会尝试恢复中断状态。

普通消息路径里：

```python
session = self.sessions.get_or_create(key)
if self._restore_runtime_checkpoint(session):
    self.sessions.save(session)
if self._restore_pending_user_turn(session):
    self.sessions.save(session)
```

system 消息路径里也有同样逻辑。

但注意，“尝试恢复”不等于真的恢复。大多数正常情况下，session 里没有：

```python
metadata["runtime_checkpoint"]
metadata["pending_user_turn"]
```

所以这两个方法会直接返回 `False`，几乎没有实际影响。

只有上一次处理这同一个 session 的消息时发生了中断，比如 agent 正在跑工具、模型刚生成回复、或者用户消息已保存但 assistant 还没回复，metadata 里才会留下这些标记。下一条消息进来时才会把它补成合法历史。

也就是说：

> 每条新消息都会检查一次；只有同一个 session 存在未完成状态时，才会真正恢复。
